## Accessibility

Every color pair in this file is checked against WCAG 2.1 AA before it is published from Figma. Body text on `--acme-neutral-0` uses `--acme-neutral-600` or darker; body text on `--acme-neutral-900` uses `--acme-neutral-300` or lighter. The primary action color, `--acme-orange-500`, is never used as small text on a light background because it fails contrast at that size — it is reserved for fills, icons at larger sizes, and borders, where the contrast requirement is looser. Focus rings use `--acme-orange-500` at 2px with a 2px offset, on every interactive component in the inventory above, including components that also use orange for their default fill; the offset keeps the ring visible even when the fill and the ring would otherwise blend into one shape.

Every component that carries a destructive action — Button.Danger, Modal.Confirm, and any row-level delete control built from Menu.Item — pairs the color signal with a text label. Color is never the only signal for a destructive action, and this is checked as part of the same accessibility pass that checks contrast, because a customer using a screen reader or a color-vision deficiency should be able to identify a destructive action from the label alone, without relying on `--acme-danger-500` being visually distinguishable from `--acme-orange-500` at a glance.

## Dark mode

ACME ships a single dark mode, not a per-customer theme system. Dark mode swaps the neutral ramp's usage — `--acme-neutral-900` becomes the page background instead of `--acme-neutral-0`, and `--acme-neutral-300` becomes the default body text instead of `--acme-neutral-600` — while the orange ramp stays anchored to the same hue. `--acme-orange-500` is used as-is in both modes for the primary action; it was chosen in part because it holds up on both a white and a near-black background without needing a separate dark-mode variant. This is a deliberate constraint on future color additions: any new brand color has to clear the same bar, checked on both backgrounds, before the figma-adapter is allowed to publish it as a token.

## Versioning

Tokens in this file are additive by default. A new token can be added in any sync without a version bump to the consuming package, because nothing existing changes. Renaming or removing a token is treated as a breaking change and is called out explicitly in the sync notes for that day, along with the component or components affected, so that a downstream consumer running `figma-adapter diff` sees exactly what moved. The component inventory follows the same rule: a new component is additive, a renamed or removed component is breaking, and the adapter's diff output distinguishes the two so a reviewer does not have to infer which kind of change they are looking at from the table alone.

## Migration notes

Earlier versions of this design system used raw hex values directly in component styles, before the token layer existed. Any component still referencing a raw hex value instead of a token is considered a defect, not a style choice, and is tracked the same way a functional bug would be tracked. The most common remaining offenders are older Table.Dense row-striping styles and a handful of Toast.Default border colors that predate the neutral ramp; both are scheduled to be re-bound to tokens rather than rewritten from scratch, since the rendered color does not need to change, only its source.

## Adapter internals

The figma-adapter that produces this file runs as a scheduled sync, not an on-demand one, so the `last-synced` date in the frontmatter reflects the most recent scheduled run rather than the most recent edit in Figma. A Figma edit made after the last sync will not appear here until the next run picks it up. The adapter resolves every variable alias to its final concrete value before writing this file, so nothing here is expressed as "same as token X" — even where two tokens happen to share a value, each is written out independently, because the adapter has no way to know from the Figma file alone whether that overlap is intentional or coincidental, and guessing would make this file less trustworthy as a source of truth, not more.

The adapter does not attempt to infer usage guidance from the Figma file's layer names or comments; every sentence of prose in this document, including the usage notes in the tables above, is authored by a human reviewing the sync output, not generated automatically. Only the tables — colors, spacing, typography, radius, elevation, and the component inventory — are adapter-generated. This split is intentional: the adapter is trusted to be accurate about values and names because those are mechanical facts pulled from Figma, but it is not trusted to explain why a value exists, because that judgment belongs to a person who understands the product, not a script that reads a design file.

## Contributing and review

Changes to the underlying Figma library go through the same review a code change would, before they ever reach this file. A designer proposing a new token or component opens a review file, links it in the design system channel, and gets sign-off from at least one other designer and one engineer who consumes the token in code. The engineer's job in that review is narrow but important: confirm the proposed value does not collide with an existing token's meaning, and confirm the naming follows the existing pattern — a color token names its role or its position in a ramp, never the component it happens to be used in first, because a token named after its first use tends to get reused somewhere the name no longer makes sense.

Component proposals get an additional check: does the new component actually need to exist, or does an existing component cover the case with a different prop or variant. ACME would rather add a variant to `Button.Primary` than ship `Button.PrimaryWide`, and the review step exists partly to catch that kind of near-duplicate before it is published and picked up by the next sync. The inventory above is meant to stay a inventory a person can read top to bottom and understand, not a list that grows without bound because adding a new component is easier than extending an old one.

Once a review is approved, the designer merges the change into the published library, and the next scheduled adapter run picks it up automatically. There is no manual step between "approved in Figma" and "appears in this file" — that gap is exactly what the adapter exists to close, and it is why this file carries a `generated-by: figma-adapter` marker in its frontmatter rather than a human author. If this file and the published Figma library ever disagree, the Figma library is the source of truth and this file is stale, not the other way around; the fix is to re-run the adapter, never to hand-edit this file to match what someone remembers Figma looking like.

Deprecating a token or component follows a slower path than adding one. A deprecation is proposed the same way an addition is, but instead of taking effect immediately, it is marked deprecated in the review file and left in place, still synced, still valid, for a full release cycle. During that window the adapter's diff output flags every consuming component and every code reference so the team doing the migration has a complete list rather than having to grep for it themselves. Only after every reference is migrated does the deprecated entry actually get removed from the library, and only then does it disappear from this file on the next sync. This is slower than simply deleting the entry, but it means nothing in the codebase silently starts referencing a token or component that no longer resolves to anything.
